# Project README structure

Based on the [Reverse Engineering & Documentation Plugin README](https://github.com/danmjrn/ReverseEngineeringDocPlugin/blob/master/README.md).

Use the same core structure for owned projects while keeping each project's facts and
operating boundaries accurate:

1. **Project title and purpose:** what the system does and who uses it; lead with behavior.
2. **Features:** grouped, concrete capabilities. Separate implemented and planned work.
3. **Requirements:** actual supported runtime, tools and external prerequisites.
4. **Settings and Configuration:** setup concepts and placeholder-only examples.
5. **Known Issues and Scope:** material limitations, maturity and verification gaps.
6. **Release Notes:** dated, factual changes tied to their actual release.
7. **Running the Project:** reproducible commands and relevant access instructions.
8. **For More Information:** architecture, operations, tests, guides and notices.

Use real screenshots when available. Describe features before the technology stack. Preserve
licenses, attribution, operational instructions and historical evidence. Documentation-only
changes do not constitute new application tests or deployment acceptance. Empty repositories
must say that implementation is pending rather than describing planned features as delivered.
